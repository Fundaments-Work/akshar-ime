## 1. The sources (all under `data/`, none in git)

| Source | What it physically is | Size |
|---|---|---|
| Aksharantar (Hindi + Nepali, merged) | 3.59M lines of `{"english word": "namaste", "native word": "नमस्ते"}` — roman spellings real users produced, paired with the correct Devanagari word; language-agnostic after strict cleaning (107,758 cross-language duplicates dropped) | ~560 MB |
| Nepali Wikipedia | raw Devanagari text lines extracted from the Wikipedia dump | ~178 MB |
| CC100 Nepali | Devanagari-heavy lines filtered from CommonCrawl | ~1.2 GB |
| News crawl | 18,190 full articles scraped from Nepali news sites (gorkhapatra, onlinekhabar, nayapatrika, …), stored in a SQLite DB | ~1.4 GB DB |

The corpus teaches *how people spell*; the running text teaches *which words
people actually use*.

## 2. What "training" means here (no neural network)

`train_model` (recipe in data/README.md) runs EM over the 3.59M merged Devanagari pairs and produces
`translit_model.bin` (~32 MB) containing exactly two learned tables:

1. **Emission table P(roman chunk | akshara)** — learned by EM (Baum-Welch).
   Each Devanagari syllable (akshara) gets a probability distribution over the
   roman chunks that can spell it: न learns `na` most likely but also `n`,
   `ना` learns `na`, `naa`, … The catch: a pair like "namaste/नमस्ते" doesn't
   say *which* letters belong to which akshara, so EM iterates — guess
   alignments from current tables, re-estimate tables from guessed alignments
   (12 passes; the math is in `2026-09-05-mathematics.md` §3).
2. **Akshara language model** — a Kneser-Ney trigram over Devanagari syllable
   sequences, counted deterministically from the segmented Devanagari side.
   It knows नम+स्ते is normal word-shape and random syllable soup is not.

Why both: the emission table maps sounds to letters; the LM scores whether the
*sequence* of syllables is a plausible Devanagari word. Neither alone is enough.

## 3. What the news data becomes (and doesn't)

The pipeline (`data/pipeline/pipeline.py count`) tokenizes the articles into:

- **Word frequencies** (524k distinct words) → exported and *merged on top of*
  Wikipedia+CC100 counts into `data/word_freq_text.bin` (708,833 words).
  This is the **prior**: when several real words match what the user typed
  (कल vs काल — the roman `kal` genuinely spells both), frequency is the only
  tiebreaker. News keeps the vocabulary current (ministers, dates, places).
- **Word-pair (bigram) counts** (6.5M rows) → `data/store/word_pairs.csv`.
  **Now used by the engine (E6, shipped):** serialized to
  `data/word_bigrams.bin` (41 MB, built by `build_bigrams.rs`); the engine
  remembers the last committed word and boosts candidates forming a corpus
  bigram with it. Measured on held-out corpus sentences: **+0.31%**
  suggestion accuracy (73,583 words; `evaluate_context` A/B harness).
- Historical note: synthetic training pairs manufactured from this vocabulary
  (self-training) were tested rigorously and made accuracy *worse*
  (model collapse) — see the 2026-09-05 experiments in the accuracy log.

## 4. How the model reaches the user

Two runtimes, same artifacts:

- **Native/IBus (Linux):** `make install` copies the engine plus
  `translit_model.bin` + `word_freq_text.bin` to `/usr/share/akshar-ime/`.
  The IBus engine calls the Rust library on every keystroke.
- **Browser/WASM:** the same Rust core compiles to `akshar_ime_bg.wasm`
  (~377 KB); the JS wrapper fetches the model files from a URL and passes the
  bytes in — everything runs offline in the tab.

Because data/ is not in the repo, **releases ship artifacts, not sources**:
CI builds only the wasm/JS on a tag push; the model bins are trained locally
(recipes in data/README.md) and attached with `make release-upload TAG=vX.Y.Z`.

## 5. What happens on each keystroke (where the data is used)

1. The typed roman prefix enters a **lattice**: every way to split `namast`
   into chunks that aksharas could have produced (emission table scores each
   edge).
2. **Beam search** walks the lattice, the akshara LM penalizing implausible
   syllable sequences.
3. The **vocabulary layer** re-ranks the k-best complete words by corpus
   frequency (`word_freq_text.bin`) — this step is worth ~+5 points of
   accuracy alone.
4. The **user dictionary** (on-device, `~/.config/akshar-devanagari/`)
   boosts words the user actually types; it learns in real time and never
   leaves the machine.
5. Top-k Devanagari suggestions are shown; accepting one feeds learning.

## 6. How evaluation data is made

The benchmark is the Aksharantar Nepali **test split** (`nep_test.json`,
4,101 cases), disjoint from training. Each case is labeled by source:
`AK-Freq` (2,108 common native words — the headline number), `AK-NEF`/`AK-NEI`
(foreign/Indian named entities — much harder, frequency can't help).
`data/eval/aksharantar_test.tsv` is the same 4,101 cases flattened to
`roman<TAB>native` for `evaluate_nepali_transliteration`; regenerate with
`python3 data/pipeline/make_eval_tsv.py`. Tuning must use `nep_valid.json`
only; `nep_test.json` is measured single-shot per experiment.

Current verified reference: **81.40% native top-1** via the full engine
(v2 reranker with embedded weights + corpus vocabulary), above IndicXlit's
published 80.25%. The offline single-shot number is 81.69%; the stricter
multi-reference benchmark (14,410 cases) is 75.29%.

## 7. Data hygiene rules (learned the hard way)

- Only `build_wordfreq_text` and `train_model` write the top-level
  `data/*.bin`; the pipeline exports into `data/store/` and merges only via
  the explicit `--merge-base` flag.
- A vocabulary that omits the test distribution (e.g. news-only) silently
  degrades accuracy by disabling the frequency prior — always rebuild from
  the full raw set.
- No data in git: releases carry artifacts, history stays clean.
